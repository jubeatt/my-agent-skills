# 清掉文件裡的墓碑

編輯文件時，產出的是**定稿，不是修訂紀錄**。改完的文件要讀起來像是「知道最終結果後，從頭
寫的一份乾淨版本」，只描述現在的設計與決定。

**墓碑（tombstone）**：功能或寫法刪掉後留下的遺跡——文件替舊設計立的碑。當讀者根本不需要
知道這段歷史，這些字就是純粹的雜訊。

## 完成判準：盲讀者測試

一個沒看過舊版、也沒看過 git 歷程的讀者，不該能從文件看出它曾被改過。看得出來，就還有墓碑
沒清乾淨。

## 墓碑長怎樣

改文件時，這類演進痕跡一律清掉：

- `不要使用 X`
- `X 已經不需要了`
- `以前使用 X，現在不要`
- `已移除 X`
- `原本是 X／已被 Y 取代／一度採用後移除／最終未採用`

## 怎麼改

- **只寫現在的做法。** 描述最終的設計與決定，不描述它怎麼演變過來的。
- **刪遺跡時連帶修上下文。** 拿掉墓碑後，順手改掉因此過期或自相矛盾的鄰近敘述（例如原本
  寫「避免 X」但最終用了 X，那句要改掉，而不是留著打架）。
- **清完掃一次殘留。** grep 剛移除或改名的東西，確認沒有失效的交叉引用；指到已移除項目的
  地方，改寫成自成一體，而不是留「原 X」這種回溯指標。

## 歷史該擺哪

墓碑之所以是墓碑，是因為**讀者不需要那段歷史**。當讀者真的需要時，歷史不是墓碑——把它放對
地方即可：

- 面向使用者、需要遷移或相容性資訊的 deprecation 警告、migration note。
- 版本演進本身就是內容的 changelog。
- 「為什麼不採用某作法」屬於長期決策依據時，寫進 ADR／設計決策紀錄，而非散在一般說明裡。

判準始終是讀者需不需要；純粹「這裡以前長這樣」的資訊，交給 git 歷史，不要留在文件正文。

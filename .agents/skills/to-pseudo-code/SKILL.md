# To Pseudo Code

把一段計畫內容（通常是某個 phase）畫成一份**骨架**：讀者打開就看得出這段會做出哪些介面、介面之間怎麼組起來、各自怎麼被使用。骨架只呈現形狀，介面內部的實作略過；唯一例外是呼叫端（見步驟 2），它的本體要寫出來，讓讀者看見新介面接走了哪些事。

## 流程

### 1. 抽出骨架

輸入是一段計畫文字，可能寫得很細，也可能只有一兩句方向。原文是方向參考：寫得細就從中抽出骨架，寫得粗就補出能達成原文目標的合理骨架；只要對齊原文要達成的目標，骨架的細節可以和原文不同。**完成判準**：列得出這段會動到的每個介面（元件、function、hook），每個都標好是新增、修改還是既有。

### 2. 組成頁面

頁面依序只有三塊，原文其他資訊（實作步驟、驗證方式、估算、取捨、待決事項）都留在原文：

1. **目標**：一句話說這段要達成什麼。
2. **圖**：依內容選，兩種都有就各畫一張。
   - **關係圖**：以元件或模組組合為主時用。畫出誰包誰、誰呼叫誰、誰被多處組合。
   - **流程圖**：以步驟流程為主時用。每一步標出負責的 function。

   每個節點帶新增／修改／既有標記。
3. **介面清單**：每個介面一段，內容是：
   - 新增／修改／既有 badge。
   - 一句話職責。
   - 簽名：用目標語言的語法寫，只放型別與宣告，型別寫完整，不求能編譯。props 有 4 個以上、或有 prop 光看名稱看不出用途時，每個 prop 後面加一行 `//` 註解說明用途。
   - 使用範例：取自實際呼叫端，幾行就好。

   **呼叫端**是把原有職責交給新增介面承接的修改介面，常見於重構抽共用（兩個重複的面板改用新的共用面板），也包括既有元件把一段邏輯抽成新 hook。只新增行為、沒有交出職責的修改介面不算。呼叫端那段在簽名之後再加兩項：
   - **改寫後的本體**：完整寫出改寫後的實作，看得出怎麼呼叫新介面、傳入什麼。
   - **職責分工**：一欄「留在這裡」，再為每個承接的新介面各開一欄「交給 X」（X 連到該介面那段），逐條列出各自負責的事。

**完成判準**：步驟 1 列出的每個介面，在圖上都有節點，在清單裡都有一段，且那段的四項都齊全；每個呼叫端另有改寫後的本體與職責分工，改寫前實作做的每件事都落在職責分工的某一欄。

### 3. 寫出 HTML

- 呈現依 [`ELEMENTS.md`](../into-html/ELEMENTS.md)：基本規則與元素規格照用，可選元素只拿來呈現上面三塊。
- 圖上每個節點都是頁內連結，點擊跳到介面清單裡對應的那段。所有連結都只指向這份 HTML 內部。
- 每個程式碼區塊都加語法高亮。
- 職責分工的各欄並排成卡片，「留在這裡」用修改的標記色、「交給 X」用新增的標記色，窄螢幕改成直排。
- **位置**：目前 git repo 的根目錄，不在 repo 裡就放工作目錄。檔名 `pseudo-<slug>.html`，slug 是描述主題的 kebab-case；同名檔已存在就覆蓋。

### 4. 交付

用 `open` 在預設瀏覽器打開，並回報檔案的完整路徑。

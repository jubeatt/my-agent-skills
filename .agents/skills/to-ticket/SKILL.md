# To Ticket

把使用者貼的資源和補充，整理成一張前端 Jira 單的 description。內容是給實作者的參考方向：講清楚要做的事和要守的規則，實作細節留給動手的人決定。

## 輸入

- **ticket key 或 URL**：必要。沒有就請使用者提供並停止。
- **使用者補充**：要做什麼的粗略說明，或直接給 Story、文件的連結。
- **參考資源**：repo 內的檔案（PDF 等）、Confluence 頁面、相關的 jira 單。

## 流程

### 1. 蒐集

Atlassian 的內容一律透過 MCP 讀。依序讀：

- **這張單**：summary、原描述、links、附件。
- **附近的單**：這張單 implements 的 Story、Story 底下的 task，以及這張單 linked 的單。範圍就停在這一圈，Epic 底下的單不展開。順著這些單的描述與 links，找出 BE 單、Figma、Confluence 文件。
- **文件**：使用者給的文件。repo 內的檔案直接讀；單子上的附件從 Jira 抓下來讀。
- **程式碼**：工作目錄是前端 repo 時，讀和這張單相關的 route、API client、型別與元件，讓實作建議對得上現況。

這一圈看完，資訊仍不夠寫出摘要和實作建議時，列出缺了什麼，請使用者提供並停止。

**完成判準**：每個來源都讀過；說得出前端要做的事；附近每張單、每個連結都判斷過要不要收進相關資源。

### 2. 寫草稿

依下方模板寫成 `ticket-<KEY>.md`，放在目前 git repo 的根目錄，不在 repo 裡就放工作目錄；同名檔已存在就覆蓋。

來源講法互相衝突時，依「使用者補充 > 文件 > 原描述」的順序取用，並在待確認記一條。

```markdown
## 相關資源

## 摘要

## 實作建議

## 規則

## 待確認
```

- **相關資源**：每行一筆，格式 `類型：[KEY 或標題](url) 標題`。只收和前端有關的：
  - Story：一律收，它是需求來源。
  - BE 單：前端會呼叫它開的 API，或依賴它的行為。
  - Figma：畫到這張單會做的畫面。
  - 文件：有這張單要遵守的流程或規則。
  - FE 單：和這張單有前後依賴。

  不符合以上條件的單（QA、DevOps、沒有依賴的 FE 兄弟單、Epic）不收。某個類型找不到就整行省略。
- **摘要**：一段話，說明情境，以及前端要做什麼。
- **實作建議**：用編號步驟寫出前端要做的事，粒度到 route、API、狀態處理、錯誤處理。實作時值得留意的點（邊界情況、安全、和現有程式碼的落差）直接寫在對應的步驟底下。
- **規則**：只在有文件時才寫這一段。
  - 每份文件一個 `###` 小標題，標題本身連到原文對應的章節；本機檔案就寫檔名。
  - 底下只列和前端有關的規則。原文有編號就寫成 `BR-xx 描述`，沒有編號就寫成一般 bullet。
  - 描述用簡短改寫或直接引原文，原文的數值、條件與術語要保留。
- **待確認**：列出衝突、缺漏的資源與疑問，給使用者看完自行刪除。沒有就省略這一段。

寫完回報檔案完整路徑，並摘要列出待確認的項目，然後等使用者確認。

**完成判準**：檔案已寫出；各 section 都依蒐集到的內容填好或依規則省略；相關資源每一筆都符合收錄條件。

### 3. 寫回 Jira

使用者確認後，重新讀一次檔案（使用者可能改過），把整份內容以 markdown 覆寫這張單的 description。只更新 description，其他欄位維持原樣。寫入後回報單子連結。

# Skill: Sync to Plan

以**實作為準，回頭校正整份 plan**，讓它隨時是一份乾淨、內部一致的計畫。重點不是「補一段進度」，
而是拿 git 的實際結果去修正 plan 的前後文。

## 核心原則

1. **diff 是「做了什麼」的真相來源。** 哪些 plan 條目該標完成／改寫，一律看 git diff，不憑印象——
   使用者可能在別的 session／用其他工具／手動改過。當前對話若有相關討論，用來理解「為什麼這樣改」、
   幫助改寫描述，但不取代 diff。一般改寫的「為什麼」只用來寫出準確的現況描述，不寫進 plan 正文；
   唯有設計反轉的來龍去脈另記入 decisions.md（見流程 step 3）。
2. **同步後是定稿，不是修訂紀錄。** plan 只描述現在的設計與決定，不留演進痕跡——墓碑式敘述的
   判準與清法依 [`tombstone-free-docs`](../tombstone-free-docs/SKILL.md)。唯一容許記錄演進的是
   decisions.md，那是 dev 期設計反轉的存放處（見流程 step 3）。
3. **就地校正，不是追加。** 該標完成的標完成、該刪的整段刪、該改寫的直接改寫，讓改完的 plan 好讀，
   而不是在結尾疊一段「更新紀錄」。
4. **順著 plan 原本的結構與標記慣例改，不套自己的模板。**
5. **只寫 `.plan/<slug>/` 底下的檔。** 對程式碼與 git 唯讀：不改 source、不 commit、不跑 build。
6. **有根據才改，不確定就問，不漏寫。** 每處修改都要對得上 diff／檔案證據。當實作偏離了
   plan／context 記錄的決策、而 diff 讀不出「為什麼」——尤其 dev 大改甚至打掉原設計時——
   先跟 dev 口頭確認再改，不臆測，也不因為看不懂就跳過不寫。

## 流程

### 1. 定位計畫檔

任務計畫在 `.plan/<slug>/`。`.plan/` 下只有一個任務資料夾就用它；有多個時**問使用者要同步哪一個**，不要自己挑。
資料夾裡 `task.md` 是主檔；搭配 gather-context 時還有 context.md／term.md／question.md。
**直接從磁碟讀**——plan 常是 untracked 或有未提交手改，磁碟上的才是使用者眼前的版本。
讀不到就**中止並請使用者指出位置**，不要自行猜測或改別的檔。

### 2. 從 git 讀出這段做了什麼

預設看最新一筆 commit：先 `git status` + `git log --oneline -n 5` 確認 HEAD 就是要同步的那筆，再 `git show HEAD`。
使用者若指定別的 commit 就用指定的。有相關未提交變更則一併看 `git diff HEAD`，並在回報時點明。

### 3. 比對計畫宣稱 vs 實際實作

**task.md** —— 逐項分類：

- **已完成**：依該 plan 慣例標完成或整段移除。
- **有偏差**：做法與原規劃不同 → 改寫描述，並修掉因此**過期或自相矛盾**的敘述
  （例如原本寫「避免 X」但實際用了 X，那句就要改掉）。
- **已失效**：不再成立的段落／檔名／假設 → 移除或改寫。
- **仍未做**：維持原樣，別誤標成完成。

**context.md** —— 實作偏離了目標／範圍／來源假設就校正成現況，維持乾淨、不留「原本想…」。
**term.md** —— 實作引入或淘汰了術語就增刪。
**question.md** —— 規劃期問答存檔，不動。

**設計反轉（打掉重練）** —— 實作發現原設計行不通、要重新設計時，「為什麼打掉」屬長期決策依據，
不塞進 context.md（會變墓碑），而是追加一筆進 `.plan/<slug>/decisions.md`（沒有就建）。
只有真的反轉才寫，小偏差不記。先依核心原則 6 跟 dev 確認來龍去脈再寫；context.md／task.md
只反映重新設計後的乾淨現況。每筆格式：

```md
## <日期> - <一句話講這個決定>
- 背景：實作時發現什麼、原設計哪裡行不通
- 決定：改用什麼做法
- 影響：連帶改了 task.md／context.md 的哪些段落
```

### 4. 就地改寫

- 做字串替換前先 `grep` 出目標行的**精確原文**（縮排／空白／全形符號常和印象不同），替換失敗就重讀該區塊拿正確字串。
- 刪整段時顧好前後銜接——分隔線、空行、章節編號別刪出破洞。

### 5. 一致性檢查

改完不只看動過的地方：

- **交叉引用**：`grep` 剛移除／改名的東西，確認沒有殘留的失效指涉。指到已移除項目的地方，
  改寫該處讓它自成一體，而不是留「原 Task 8」這種回溯指標。
- **編號／順序**：移除某段後，檢查是否影響後續編號或「放最後」之類的相對描述。
- **可讀性**：通讀改動區塊，確認讀起來仍像一份完整計畫。

### 6. 回報

摘要同步了什麼：task.md 哪些標完成／移除、context.md／term.md 改了什麼、有沒有新增 decisions.md 條目，
以及有無因未提交變更、決策偏離或改動意圖不明而需 dev 確認的地方。
